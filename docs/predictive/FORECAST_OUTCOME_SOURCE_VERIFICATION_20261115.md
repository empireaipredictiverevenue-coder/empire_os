### REV078 forecast horizon and replay correctness — 15 November 20:50 UTC

The existing enterprise forecast scorecard defines the target-day contract as `forecast_registered_at.date() + horizon_days == target_day`. Previously the **held** REV078 migration instead computed target from `p_observed_through + horizon_days`, confusing the input observation day with issue time. This could reject valid one-day forecasts based on two-day-old (but still recent) input data, or silently target a different day from the original enterprise scorecard. The staged REV078 now computes `target_day = registration_utc_day + horizon_days`, preserves `observed_through_utc` separately, and marks `horizon_basis=registration_utc_day` in its stored evidence. Target is always future; observed input is bounded and stale beyond seven days is denied.

After aligning the horizon, the deterministic key was also corrected: it now identifies a unique **tenant / model / version / target UTC day / horizon**. A caller cannot create competing predictions for the same target by varying `p_observed_through`. Exact REV076+REV077+REV078 executable PostgreSQL 18 tests verified both tenants see the expected target-day relation, a recent two-day-old source can support a one-day-ahead forecast, duplicate submissions from an alternative source day fail unique constraints, and immutable business role DML denial persists. A separate 12-row **synthetic** supplied cohort was accepted by the existing enterprise scorecard as numeric diagnostics only; its independent source, financial accuracy and customer release flags remained FALSE.

This is a code/semantic correction to the **HELD** EmpireDB release candidate. It is not an authenticated customer forecast or measurable commercial calibration. No production DDL, customer data, backup schedule or service was changed.
